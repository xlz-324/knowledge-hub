# ADR-0001：模块化单体、前后端分离与 pnpm workspace

- 日期：2026-11-16
- 状态：Accepted

## 背景

KnowledgeHub 是少量用户使用的自部署知识库，也是全栈与 AI 应用学习项目。需要独立练习 React、NestJS、Worker 和部署，但没有微服务、多团队或高并发需求。服务器目标为 2C4G，不能让基础设施占用核心学习时间。

## 决策

- 一个 Git monorepo 中保存 `apps/web` React SPA 与 `apps/api` NestJS 模块化单体。
- Web 与 API 是独立应用，分别构建和运行；浏览器只通过 HTTP 调用 API，不能访问数据库或后端密钥。
- 使用 Vite 和 NestJS 官方脚手架生成应用，不手工复制框架初始化代码。
- pnpm workspace 负责包边界、依赖链接、统一锁文件和根脚本。
- 暂不引入 Turborepo/Nx，也不创建没有实际共享内容的公共包。
- 生产采用同源部署，Nginx 托管 Web 构建产物并反向代理 API；API 与后续 Worker 同代码库、同版本。
- PostgreSQL 保存业务事实，后续承担精简任务队列与 pgvector 向量存储。
- Redis/BullMQ、微服务和生产 K8s 后置。

## 备选方案

- Next.js 全栈：减少应用数量，但不符合独立后端/Worker 的学习目标。
- 微服务：当前缺少收益，会增加网络、部署和数据一致性成本。
- Turborepo/Nx：任务缓存、依赖图和代码生成有价值，但当前仅两个应用，没有构建性能问题。
- Redis/BullMQ 起步：任务量小，先用 PostgreSQL 学习持久化任务、锁、幂等与恢复。

## 取舍

维护两个应用比单框架全栈多一些配置，但业务边界和部署边界更清楚。pnpm workspace 不提供 Turborepo/Nx 的完整构建缓存与依赖图；接受现阶段根脚本直接调用两个应用，出现可测量的构建或协作问题再增加工具。

## 影响

- 每个应用有自己的 `package.json`、依赖、测试和构建。
- 共享代码只有在确有需求时才进入 `packages/`。
- 新资源必须加入权限测试矩阵；前后端分离不能替代服务端权限。
- 健康检查必须真实经过 HTTP，后端失败时前端不得显示正常。
- 不在一期创建二期学习/面试模块、空表或占位 API。

## 验证与重审条件

- 干净克隆后可按 README 安装、启动、测试和构建。
- API 就绪检查及异常响应经过真实 HTTP 测试。
- 应用或共享包增多、构建明显变慢、需要受影响任务选择或依赖图时，评估 Turborepo/Nx。
- 出现可测量的扩展瓶颈时另写 ADR，不预先拆分微服务。
